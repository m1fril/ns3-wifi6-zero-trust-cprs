# sim-orchestrator

Оркестратор, генератор нагрузки, самопроверка и веб-UI для `scratch/network-project` (ns-3.46.1).
Поддерживаются две топологии:

| | `infra` (по умолчанию) | `mesh` |
|---|---|---|
| Схема | Gateway ─p2p─ AP ─Wi-Fi─ STA (звезда вокруг каждой AP) | 802.11s mesh: каждый узел — маршрутизатор, данные идут через соседей |
| Стандарт | 802.11ax, 80 МГц, 5 ГГц | 802.11a, 20 МГц, 5 ГГц (mesh-интерфейсы ns-3 поддерживают только non-HT PHY) |
| Маршрутизация | нет, 1 хоп | HWMP (reactive), peer links (802.11s PMP) |
| Транспорт | сырые L2-кадры (`PacketSocket`) STA → AP | UDP/IPv4 узел → ближайший шлюз, 1…N хопов |
| `nAps` | точки доступа | шлюзы (приёмники трафика), они же ретрансляторы |
| `nStas` | станции | mesh-маршрутизаторы |
| `cell:N` | станции AP N | узлы, у которых ближайший шлюз — `ap:N` |
| Размещение | случайное блуждание вокруг AP | сетка (`meshSpacing`) или случайное (`roomSize`), статично |

## Исходный проект

| Компонент | Роль |
|---|---|
| `scratch/network-project/network-project-main.cc` | Точка входа, CLI-флаги ns-3 (`--nAps`, `--nStas`, `--scenario`, ...) |
| `simulation-environment.*` | Построение топологии, трассировки, CSV-лог |
| `agent-orchestrator.*` | Heartbeat 100 мс, вызывает `Tick()` у агентов |
| `director/chaos/linear-escalation/targeted-loss/telemetry-agent.*` | Сценарные агенты |
| `traffic-app.*`, `timeline-agent.*` | Добавлены: генератор трафика с netem и исполнитель таймлайна |
| `run_*.sh`, `analyze_*.py`, `conference-2026/sim/` | Прежние кампании и анализ |

Вся сеть живёт в одном процессе ns-3 (дискретно-событийная симуляция). Выход: `Bianchi-*-Events.csv`
(`Time_s,NodeID,NodeType,Action,Value`). Без `--timeline` и `--topology=mesh` бинарник ведёт себя как
раньше: CSV старых сценариев побайтно совпадают с исходным бинарником (проверено MD5).

## Архитектура

```
config*.yaml ─► orchestrator.py ─► loadgen.py (правила, seed) ─► runs/<name>/<i>/timeline.txt
                    │                                                     │
                    │ Popen × replicas (max_parallel), restart, SIGTERM   ▼
                    └──────────────► network-project-main --timeline=... [--topology=mesh]
                                          TimelineAgent ─► SimulationEnvironment / TrafficApp
                    orchestrator.py ctl ─(дописывает "now ..." в timeline.txt)─┘
verify.py ◄── stdout.log + CSV          ui.py ── браузер (127.0.0.1:8765)
```

- **Процесс** = один экземпляр сети. Оркестратор поднимает `replicas` процессов (seed = `base_seed + i`),
  держит не больше `max_parallel`, перезапускает упавшие, на SIGINT/SIGTERM шлёт детям SIGTERM, через
  `grace_period_s` — SIGKILL. Симуляция ловит SIGTERM и корректно закрывает CSV.
- **Узлы**: пул создаётся заранее; churn и масштабирование выключают/включают радио
  (`WifiPhy::SetOffMode/ResumeFromOff`) и трафик. В infra станция переподключается к AP (`REASSOC`),
  в mesh соседи закрывают peer links и HWMP ищет обходной маршрут.
- **Трафик** (`TrafficApp`): размер и интервал каждого пакета разыгрываются из распределения, burst —
  N пакетов подряд с шагом `gap_us`.
- **Сетевые условия**: netem-подобная стадия на выходе отправителя — задержка, джиттер, потери,
  изоляция. Пакет считается отправленным до netem, поэтому потери видны в PDR, а задержка — в latency.

## Установка и запуск

```bash
cd ns-allinone-3.46.1/ns-3.46.1
./ns3 build network-project-main          # собрать симуляцию
python3 -m pip install pyyaml             # для *.yaml; *.json работает и без него
cd sim-orchestrator
python3 test_loadgen.py                   # самопроверка генератора
python3 orchestrator.py run               # infra: 3 реплики × 60 с, ~1.5 мин
python3 orchestrator.py run -c config.mesh.yaml   # mesh: 25 узлов, ~20 с
python3 verify.py runs/mesh-demo          # сверка выхода с входом
python3 ui.py                             # веб-UI: http://127.0.0.1:8765
```

Полезное:

```bash
python3 orchestrator.py run --set churn.rate_per_s=2 --set run.replicas=10 --set run.name=heavy
python3 orchestrator.py run -c config.mesh.yaml --set sim.args.meshSpacing=25
python3 orchestrator.py run --dry-run                    # только сгенерировать таймлайны
python3 orchestrator.py gen --seed 5 | less              # посмотреть таймлайн
python3 orchestrator.py ctl runs/demo/000 NODE sta:3 down   # live (осмысленно с realtime: 1)
```

Результаты: `runs/<name>/<i>/` (`timeline.txt`, `cmd.txt`, `stdout.log`, CSV), `summary.json`
(PDR, throughput, p95, активные узлы, отказы, потери по причинам, хопы, peer links, поиски маршрутов),
`verify.json` после проверки.

## Mesh: на что обратить внимание

**Радиобюджет.** 802.11a, 16 дБм, log-distance с показателем 3: порог обнаружения преамбулы в ns-3
(−82 дБм) достигается на ~51 м. Шаг сетки определяет связность:

| `meshSpacing` | соседи по прямой | по диагонали | через одного | итог |
|---|---|---|---|---|
| 25 м | −72.6 дБм | −77.1 дБм | −81.6 дБм (на грани) | лишние неустойчивые линки |
| **30 м** | −75.0 дБм | −79.4 дБм | вне зоны | 8 соседей, устойчиво (по умолчанию) |
| 40 м | −78.7 дБм | вне зоны | вне зоны | 4 соседа, больше хопов |
| 50 м | −81.6 дБм (на грани) | вне зоны | вне зоны | линки постоянно рвутся |

**Peer links.** По умолчанию dot11s в ns-3 закрывает линк после 2 потерянных биконов или 2 подряд
неудачных кадров. Под нагрузкой биконы (широковещательные кадры без повторов) теряются в коллизиях, и
линки «мигают»: в тесте на 30 с было 588 закрытий и 503 поиска маршрута. В `config.mesh.yaml` пороги
явно подняты до 10 (`ns3::dot11s::PeerLink::MaxBeaconLoss`, `MaxPacketFailure`), что ближе к Linux
mac80211; закрытий стало 16. Чтобы изучать поведение по умолчанию, уберите эти две строки.

**ARP** для шлюзов заполнен статически (как на заранее настроенных mesh-маршрутизаторах), чтобы
ARP-флуд по mesh не искажал измерения. **Число хопов** считается по количеству передач пакета MAC-уровнем
(источник + каждый ретранслятор) и пишется как `HOPS_MEAN` по секундам.

## Самопроверка (`verify.py`)

Независимая модель проигрывает фактически выполненный таймлайн (из `stdout.log`, включая live-команды)
вместе с агентами director/chaos/escalation с шагом 1 мс и сравнивает с CSV:

| Проверка | Что сравнивается | PASS |
|---|---|---|
| generated packets vs model | число сгенерированных пакетов против суммы интенсивностей профилей | ±3% |
| per-second load shape | корреляция модели и факта по секундам | r ≥ 0.95 |
| active STAs vs timeline | число активных узлов каждую секунду | ≥ 95% секунд точно |
| netem drops vs model | потери netem/изоляции против заданных вероятностей | ±max(5%, 4σ) |
| loss accounting | отправлено − принято = сумма залогированных причин | необъяснённых ≤ 1% |
| netem p95 latency | p95 задержки против смеси нормальных распределений netem | ±15% (в mesh — справочно) |

Причины потерь в CSV (`compactMetrics=1`, по секундам): `NETEM_DROP_COUNT`, `WIFI_DROP` (MAC: станция не
подключена), `RETRY_DROP_COUNT` (MAC: исчерпаны повторы), `QUEUE_DROP_COUNT` (MAC: переполнение или
истечение времени жизни в очереди), `STACK_DROP_COUNT` (mesh: IP, очередь traffic-control, отказ сокета).
Итог по узлу в конце прогона: `HWMP_DROPPED` / `HWMP_DROPPED_TTL` (нет маршрута, очередь HWMP, TTL;
включает служебные кадры) и `PEER_FILTER_DROPPED` (кадр данных от соседа с уже неактивным peer-link).

Не трассируется в ns-3 вовсе: при полной очереди MAC планировщик `FcfsWifiQueueScheduler` вытесняет
самый старый кадр данных ради служебного кадра (PREQ/PERR). При перегрузке это 10–13% потерь; `verify.py`
в таком случае (очередь насыщена) ставит WARN с пояснением, а не FAIL.

## Кампании экспериментов (`campaign.py`, `analyze_campaign.py`)

Серии по ~100 прогонов на mesh-топологии; параметры каждого прогона разыгрываются от строки
`<режим>:<seed>:<номер>`, поэтому кампания воспроизводима. Длительность по умолчанию 300 с модельного
времени (на одном ядре такой прогон считается 1,5–2 мин).

| Режим | Прогонов | Что разыгрывается |
|---|---|---|
| `normal` | 100 | 16–36 маршрутизаторов, 1–3 шлюза, шаг 25–40 м, нагрузка ×0,5–1,5, задержка/джиттер/потери на 20–60% узлов |
| `single_failure` | 100 | отказ одного из 3 шлюзов (50) или моста между двумя кластерами (50, `meshLayout=corridor`) |
| `collapse` | 100 | потеря единственного шлюза, отказ 70–95% маршрутизаторов, перегрузка 1400 Б каждые 1–4 мс |
| `load` | 100 | 5 размеров пакета × 5 интервалов × 4 seed на сетке 5×5 |
| `density` | 120 | 15–40 узлов на квадрате 60…400 м, случайное размещение, лёгкий churn |

```bash
python3 campaign.py all --parallel 8          # или один режим: campaign.py normal --n 100
python3 analyze_campaign.py runs/campaign-*   # results.csv + anomalies.json на прогон
python3 verify.py runs/campaign-normal
```

`analyze_campaign.py` считает PDR в окнах «до» (10 с … событие) и «после» (событие + 5 с … конец),
долю доставляемого трафика (скорость доставки после / до) и ищет аномалии: всплески задержки, провалы
доставки, отрезанные узлы (шлют ≥ 10 с подряд, ничего не доходит), пачки закрытий peer-link, штормы
поиска маршрутов (≥ 20/с три секунды подряд; короткие всплески — штатное обновление путей HWMP раз в ~5 с),
перегретые ретрансляторы. Соседние секунды склеиваются в эпизоды; эпизод в пределах −1…+15 с от
внесённого события помечается `induced`, остальные — `spontaneous`.

**Поузловые метрики** (`compactMetrics=1`, каждую секунду): `NODE_SENT`, `NODE_RECV`, `NODE_LAT_MS`,
`NODE_HOPS`, `NODE_FWD` (ретранслировано для других), `NODE_DROP` (собственные потери с известной причиной).

### Воспроизведение статьи «Імітаційне моделювання стійкості mesh-мереж до умов перевантаження вузлів»

Все числа статьи получены этими командами (ns-3.46.1, `./ns3 build scratch/network-project/network-project-main`
из корня ns-3). В репозитории лежат итоговые таблицы каждой серии (`runs/*/results.csv`, `config.resolved.json`,
`verify.json`); сырые поузловые CSV (~0,9 ГБ) не версионируются и пересчитываются командами ниже.

```bash
python3 campaign.py all --parallel 8                           # 520 прогонов основной кампании
P=sim.args.ns3::dot11s::PeerLink                               # серия плотности с таймерами как в Linux
python3 campaign.py density --tag linux --parallel 8 \
  --set "$P::RetryTimeout=+100ms" --set "$P::ConfirmTimeout=+100ms" \
  --set "$P::HoldingTimeout=+100ms" --set "$P::MaxRetries=3"
python3 analyze_campaign.py runs/campaign-*                    # results.csv на серию
python3 verify.py runs/campaign-normal                          # самопроверка (любой серии)
python3 warehouse.py                                            # пример склада 100 × 100 м -> runs/warehouse/results.csv
```

Таймеры peer-link: по умолчанию ns-3 использует 40 TU (≈ 41 мс) без случайной составляющей; при ≥ 27 узлах в
зоне связи рукопожатие Open/Confirm не успевает и плотная сеть коллапсирует. Значения 100 мс и 3 повтора взяты
из Linux mac80211 (`net/wireless/mesh.c`). Полную статистику HWMP/peer management по узлам выгружает
переменная окружения `MESH_REPORT=<файл>`.

## Веб-UI (`ui.py`)

Интерфейс на английском, только stdlib, слушает 127.0.0.1 и отклоняет чужие Host/Origin:
- выбор конфига (`config.yaml`, `config.mesh.yaml`, любой `*.yaml/*.json` рядом), запуск и остановка;
- таблица инстансов с прогрессом и KPI, кнопка **Verify** с результатами проверок;
- графики по секундам с общим перекрестием: активные узлы, throughput, PDR, p95, число хопов (mesh),
  потери по причинам (stacked) с таблицей итогов;
- **карта mesh-топологии**: узлы и шлюзы, ячейки, открытые peer links и упавшие узлы в выбранный момент
  (ползунок или наведение на график);
- **панель узла** (клик по узлу на карте): состояние, peer links, отправлено/доставлено/PDR, задержка,
  хопы, ретрансляция, потери в выбранную секунду + графики узла за весь прогон с отметкой периодов,
  когда он был выключен; кнопка подставляет `NODE sta:N up/down` в live-управление;
- live-команды, просмотр stdout / timeline / orchestrator.log, редактор конфигов с проверкой.

## Команды таймлайна

Формат строки: `<время_с | now> <КОМАНДА> <цель> <аргументы>`. Цель: `sta:3`, `sta:0-9`, `sta:*`, `ap:1`,
`ap:*`, `cell:2`, `all`.

| Команда | Действие |
|---|---|
| `NODE <цель> up\|down\|restart [простой_с]` | Включить/выключить узел (STA/маршрутизатор или AP/шлюз) |
| `APP <sta> on\|off` | Включить/выключить сервис трафика на узле |
| `TRAFFIC <sta> size=<dist> interval=<dist>` | Горячая замена профиля трафика (интервал в мкс) |
| `BURST <sta> <пакетов> <шаг_мкс>` | Импульсный всплеск |
| `NETEM <sta> <задержка_мс> <джиттер_мс> <потери>` | Сетевые условия (`0 0 0` — сброс) |
| `ISOLATE <sta> on\|off` | Изоляция сегмента (все пакеты отбрасываются) |
| `AGENT <director\|chaos\|escalation\|targeted_loss\|telemetry> on\|off` | Включение/отключение модуля |
| `MODE normal\|controlled\|failure\|escalation` | Переключить режим (на него реагируют chaos/escalation) |
| `STOP` | Завершить симуляцию |

`<dist>`: `const:V`, `uniform:MIN:MAX`, `normal:MEAN:STD[:MIN:MAX]`, `exp:MEAN[:MAX]` (пуассоновский поток).
В `script` конфига `@имя_профиля` раскрывается в `size=... interval=...`. Максимальный размер пакета:
2296 Б в infra, 1472 Б в mesh (UDP/IPv4 поверх MTU 1500).

## Ограничения

- Агент `chaos` в режимах `controlled`/`failure` каждые 100 мс задаёт **всем** STA постоянный интервал,
  перекрывая профили — после выхода из режима профили нужно переназначить (см. `config.yaml`).
- Если правило `network.rules` и случайный эпизод пересекаются на одной STA, побеждает более поздний сброс.
- Netem и изоляция применяются на стороне отправителя: трафик только uplink, этого достаточно.
- Новые узлы не создаются на лету — масштабирование идёт в пределах пула `nStas`.
- Mesh: шлюз закреплён за узлом по расстоянию при старте. При отказе шлюза его узлы не
  переключаются на другой — их трафик теряется до возврата шлюза (`HWMP_DROPPED`).
- Mesh-узлы статичны; агенты chaos/escalation меняют только нагрузку, скорость движения для них не действует.
- UI показывает прогоны из `run.output_dir` конфига по умолчанию (у обоих примеров это `runs/`).
